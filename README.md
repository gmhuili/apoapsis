# apoapsis

*The point in an orbit of greatest distance — where you see the whole system at
once, and where a small burn changes everything downstream.*

A free-forever static site for technical writing — code reviews, teardowns,
essays, explainers and dated forecasts — plus a Python CLI that indexes every
piece and its video, and pushes copies to other platforms.

`repocast` produces. **apoapsis** holds the canonical copy and distributes it.

The site is the hub. repocast produces the article and the video; `apo import`
adopts that output as a post; `apo syndicate` pushes copies outward and writes
every resulting URL back into the post's own front matter, so the canonical
page is the one place that knows where all the copies live.

```
repocast run <repo>
        │  article.md, video.mp4, short.mp4, cover.png, publish.json
        ▼
apo import out/<repo>          → page bundle with taxonomy + video reference
apo check                      → front-matter validation
apo deploy <slug>              → git push → GitHub Actions → GitHub Pages
apo syndicate <slug>           → dev.to, Medium, YouTube
        │
        └─ writes links: {...} back into front matter
                ▼
        next build renders the "Also on" row
```

## What "free" actually means here

Every asset class this site produces, and where it lives:

| Asset | Where it lives | Cost | Ceiling |
|---|---|---|---|
| HTML, CSS, JS | GitHub Pages | $0 | 1 GB published site |
| Markdown source, config | GitHub repo | $0 | 1 GB recommended for a Pages source |
| Builds | GitHub Actions | $0 | **Unlimited minutes on public repos** |
| Search index | Pagefind, static files in the site | $0 | counts toward the 1 GB |
| **Video** | **YouTube** | **$0** | **Unlimited; never touches your host** |
| Thumbnails, diagrams | GitHub repo | $0 | counts toward the 1 GB |
| Comments | GitHub Discussions via giscus | $0 | none in practice |
| TLS certificate | GitHub Pages, automatic | $0 | — |
| Bandwidth | GitHub Pages | $0 | 100 GB/month soft limit |
| RSS feed | generated by Hugo | $0 | — |
| Syndicated copies | dev.to, Medium, YouTube | $0 | — |

Total: **$0/month.** No card, no trial clock, no free tier that expires.

### Why video never costs you anything

This is the single most important storage decision in the project, and it is
why `apo import` **references** the mp4 rather than copying it.

A rendered video is 100–500 MB. GitHub Pages caps a published site at 1 GB, so
two or three videos would exhaust it — and because git keeps history forever,
committing a video makes the repo permanently larger even after you delete it.

So the video is uploaded to YouTube, which stores it for free at any volume,
and the site embeds an iframe. The bytes on your host are a few hundred for the
embed markup. Front matter keeps `video_file` pointing at wherever repocast
left the file on your own disk; only the YouTube URL is ever published.

Practical consequence: text posts run about 20–80 KB each. You would need
roughly ten thousand posts to approach the 1 GB ceiling, and video never counts
against it at all.

### The two things that can cost money

Both optional, neither required:

1. **A custom domain** — about $10–15/year at a registrar. `YOURNAME.github.io`
   is free forever and works fine. GitHub charges nothing to attach a domain
   and issues the certificate free either way.
2. **LLM and image-generation API calls in repocast** — only if you point it at
   a hosted provider. Running Ollama locally makes this $0 too, and `edge-tts`
   is free for narration.

Analytics are not included. If you want them free, GoatCounter and Cloudflare
Web Analytics both have genuinely free tiers; neither needs a server.

### Where the free-tier claim would break

Being precise about the edges, since "free" is load-bearing here:

- Exceeding 100 GB/month of bandwidth. That is a soft limit and would take
  serious traffic; GitHub asks you to move rather than billing you.
- Making the repo **private**. Actions minutes are only unlimited on public
  repos; private repos get 2,000 minutes/month free, which is still ~2,000
  builds, but it is a real ceiling.
- Using Pages to run a business or a hosting service — prohibited by the terms
  regardless of size. A personal or organisational publication is fine.

## Setup

### 1. Repository and hosting

```bash
git init && git add -A && git commit -m "initial"
gh repo create YOURNAME.github.io --public --source=. --push
```

In the repo's **Settings → Pages**, set **Source: GitHub Actions**. Then edit
`site/hugo.toml` and `apoapsis.toml`, replacing `YOURNAME` with your account.

### 2. Theme

```bash
git submodule add --depth=1 https://github.com/adityatelange/hugo-PaperMod \
    site/themes/PaperMod
```

PaperMod requires **Hugo 0.146 or newer**. The workflow pins 0.152.0. If you
build locally, install a matching version — older Hugo fails outright, because
0.146 moved template lookup to `layouts/_partials/` and `layouts/_shortcodes/`.

### 3. apoapsis

```bash
cd apoapsis && pip install -e .            # add [youtube] for uploads
cp ../apoapsis.toml.example ../apoapsis.toml
```

`apoapsis.toml` holds no secrets — only the *names* of environment variables
that hold them, so it is safe to commit. Export the real values in your shell:

```bash
export DEVTO_API_KEY=...
```

## Comments

Comments are GitHub Discussions, rendered by giscus. No server, no database,
and readers sign in with an account they already have.

1. Enable **Discussions** on the repo (Settings → Features).
2. Install the giscus app: https://github.com/apps/giscus
3. Visit https://giscus.app, enter the repo, and copy the four values it gives
   you into `[params.giscus]` in `site/hugo.toml`.

The partial renders nothing until `repo` and `repoId` are both set, so an
unconfigured site builds clean rather than erroring. Set `comments: false` in
a post's front matter to silence a single page, and the thread is excluded
from the search index either way.

giscus follows the site's light/dark toggle automatically.

## Content model

### Post kinds

Content types are declared, not hardcoded. `apo kinds` lists them:

| Kind | What it is |
|---|---|
| `code-review` | A close reading of a specific codebase |
| `essay` | An argument about engineering practice |
| `forecast` | A dated, falsifiable prediction |
| `teardown` | Taking a system or protocol apart |
| `explainer` | Teaching one concept properly |
| `retrospective` | Scoring an earlier forecast |
| `note` | A short observation, no outline |

Each kind supplies the default category, a skeleton outline, and any extra
front matter. Add your own — or override a built-in — under `[kinds.*]` in
`apoapsis.toml`; no code change needed.

```bash
apo new "Why io_uring did not kill epoll" -k essay -u linux -t linux
apo new "RISC-V displaces ARM in automotive by 2030" -k forecast
```

> The front-matter field is `post_kind`, **not** `kind`. Hugo reserves `kind`
> (and `type`) for its own page-kind resolution; using it fails the build with
> `unknown kind "forecast" in front matter`.

### Forecasts are held to account

A forecast is only worth writing if it can be scored. The `forecast` kind
requires `horizon`, `confidence` and `review_on`, and `apo check` refuses to
publish without them. `{{< forecast >}}` renders the terms as a card, and
`/forecasts/` is a live scoreboard splitting predictions into **due for
review**, **open** and **scored**. Set `resolved: correct | wrong | partial`
when the time comes, and write the post-mortem as a `retrospective`.

### Taxonomies

Four taxonomies, all filterable in search:

- **category** — the coarse bucket, one per kind: `code-review`, `essay`,
  `forecast`, `teardown`, `explainer`, `retrospective`, `note`
- **series** — an ordered multi-part arc, e.g. "Reading ORB-SLAM3"
- **subject** — the fine-grained topic: `slam`, `lock-free-queues`
- **tag** — portable keywords; kept lowercase alphanumeric and capped at 4,
  because that is what dev.to accepts

Series ordering comes from `series_order` in front matter. Both the in-post
series box and the `/series/<name>/` page sort by it.

> A note for anyone editing the templates: use `.Pages.ByParam "series_order"`,
> **not** `sort .Pages "Params.series_order"`. The latter silently returns the
> wrong order.

## Commands

The CLI installs two identical entry points: `apoapsis` and the short alias
`apo`. Everything below uses `apo`.

| Command | What it does |
|---|---|
| `apo kinds` | List the content types this site publishes |
| `apo new "Title" -k forecast -u subject -t tag` | Scaffold a post bundle |
| `apo import out/repo -s "Series"` | Adopt a repocast run |
| `apo check [slug]` | Validate front matter |
| `apo preview` | Local server with drafts |
| `apo build` | Build site + search index |
| `apo deploy <slug>` | Undraft, commit, push |
| `apo video <slug>` | Render video via repocast |
| `apo syndicate <slug> [--dry-run]` | Cross-post, then write links back |
| `apo publish <slug> --with-video` | Everything, in order |
| `apo status [slug]` | Where each post has been published |

`--dry-run` on `syndicate` shows exactly what would happen and changes nothing.
Start there.

## Idempotency

`.apoapsis-state.json` maps each slug to the article IDs it created on each
platform. A second `syndicate` **updates** the existing dev.to article rather
than creating a duplicate. Delete a slug's entry to force a fresh post.

## repocast integration

`apo import` discovers artifacts by glob, so repocast can reorganise its output
without breaking publication. Override any pattern under `[repocast]` in
`apoapsis.toml`.

Video files are **referenced, not copied**. A 200 MB mp4 in the content tree
would bloat the git repo for no benefit — YouTube hosts the video and the site
embeds it. Thumbnails are small, so those are copied into the page bundle and
used as the cover image. Pass `--copy-video` if you want the file local anyway.

For rendering, point `apo video` at repocast:

```toml
[targets.youtube]
render_command = "repocast run {repo} --out build/video/{slug}"
```

Placeholders available: `{script}`, `{output}`, `{repo}`, `{slug}`, `{title}`.

## Embedding the video

`apo import` puts `{{< video >}}` at the top of the body. It reads the YouTube
ID from `links.youtube`, so it renders nothing until the video is actually
uploaded and stays silent on essays that have no video. Move the shortcode
anywhere in the post you like.

## On earning from this

Worth setting expectations honestly. YouTube's Partner Program needs 1,000
subscribers plus 4,000 public watch hours in 12 months. Medium pays on member
read time, which for deep technical writing means a small, engaged audience
rather than a large one. Neither is quick.

The realistic near-term return on this kind of writing is credibility —
inbound consulting, job conversations, conference invitations. Publishing to
dev.to and YouTube widens that funnel considerably compared with a blog nobody
finds, which is the actual argument for the syndication pipeline. Treat ad
revenue as a lagging bonus rather than the goal.

Canonical URLs matter for this. Every syndicated copy points `rel=canonical`
back at your domain, so search engines credit the original and your own site
accumulates authority instead of competing with the copies.
